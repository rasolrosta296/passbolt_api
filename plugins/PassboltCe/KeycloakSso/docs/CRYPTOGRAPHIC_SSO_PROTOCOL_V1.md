# Keycloak cryptographic SSO protocol v1

Status: frozen for Milestone 4 implementation. This document does not change Passbolt's authentication authority.

## Security boundary

OIDC proves control of a linked Keycloak identity. It never creates a Passbolt identity, session, JWT, or refresh token. Releasing the server share also never authenticates Passbolt. Only the existing, unchanged GPGAuth/GPG-JWT challenge proof establishes Passbolt authentication.

Keycloak never receives Passbolt private keys, passphrases, client or server envelope keys, or vault plaintext. The API never receives the client key, plaintext passphrase, decrypted private key, or vault plaintext. The browser extension is the only context in which the passphrase and decrypted OpenPGP private key may briefly exist.

## Versioned context

`ContextV1` is deterministic RFC 8949 CBOR containing exactly one fixed positional array of nine text strings:

1. `protocol_version`
2. `crypto_suite`
3. `passbolt_origin`
4. `user_uuid`
5. `identity_uuid`
6. `enrollment_uuid`
7. `client_enrollment_uuid`
8. `openpgp_fingerprint`
9. `enrollment_public_key_thumbprint`

The version is `passbolt-keycloak-sso-v1`. The suite is `AES-256-GCM+HPKE-P256-HKDF-SHA256-AES128GCM`. Decoders reject non-text values, maps, tags, indefinite lengths, optional or unknown fields, non-canonical encodings, and trailing data. Accepted bytes must equal a deterministic re-encoding using a constant-time comparison.

UUID fields use canonical lowercase RFC 4122/RFC 9562 text with the RFC variant and versions 1 through 8. This accommodates Passbolt server-generated UUIDv7 identifiers; the extension-generated `client_enrollment_uuid` remains a fresh UUIDv4. Nil, non-RFC-variant, uppercase, and non-canonical UUID text is rejected. This validation rule does not change the approved encoded test-vector bytes.

Domain-bound messages are deterministic CBOR arrays `[domain, ContextV1]`, using these exact domains:

- `passbolt-keycloak-sso-v1/inner-aead`
- `passbolt-keycloak-sso-v1/outer-aead`
- `passbolt-keycloak-sso-v1/enrollment-transcript`
- `passbolt-keycloak-sso-v1/device-login`
- `passbolt-keycloak-sso-v1/release-package`
- `passbolt-keycloak-sso-v1/context-hash`

Request transcripts use the approved amended outer framing `[[domain, ContextV1], [request values]]`. Each operation has a separate fixed positional schema; all values are mandatory CBOR text strings:

- Enrollment transcript: `[[enrollment-transcript, ContextV1], [client_blob_digest, server_share_digest]]`.
- Browser-profile login transcript: `[[device-login, ContextV1], [client_nonce, hpke_recipient_public_key, client_blob_digest]]`.
- Release-package transcript: `[[release-package, ContextV1], [client_nonce, hpke_recipient_public_key, request_id]]`.

There is no generic wire-level request array. Implementations call operation-specific encoders and decoders, require the exact arity and order above, deterministically re-encode, and compare the received bytes exactly. The server-share at-rest AEAD uses the unamended `[release-package, ContextV1]` binding as AAD.

## Keys and persisted artifacts

- `KD`: 256-bit AES-GCM key generated by WebCrypto with `extractable=false`. It is a profile-resident non-extractable key persisted by IndexedDB structured clone.
- Enrollment signing key: ECDSA P-256 key generated by WebCrypto with `extractable=false` for the private key. It is a profile-resident non-extractable key persisted by IndexedDB; only its public JWK is sent to the API.
- `KS`: independent 256-bit AES-GCM key generated in the extension. It is extractable only during enrollment upload and is never persisted in plaintext by the browser.
- Server share protection: XChaCha20-Poly1305-IETF under a deployment KEK selected by explicit key ID. The active KEK encrypts; old keys are decrypt-only.
- Release transport: RFC 9180 base mode with DHKEM(P-256, HKDF-SHA-256), HKDF-SHA-256, and AES-128-GCM, as frozen by the compatibility prototype.

The extension persists `KD`, the signing private key, `C2`, independent 96-bit inner and outer IVs, canonical context, and public enrollment metadata. The API persists only encrypted `KS`, its KEK key ID and nonce, the signing public key and thumbprint, the SHA-256 digest of `C2`, context metadata, and ownership/status fields. Enrollment foreign keys cascade on hard deletion of their owning user or identity so orphaned encrypted shares cannot survive owner erasure; the authenticated unlink flow nevertheless locks, revokes, overwrites, and explicitly deletes enrollment rows before removing the identity.

## Enrollment

Enrollment requires both an active normal GPGAuth-created Passbolt session and a fresh, one-time, purpose-bound OIDC proof for the already linked issuer and subject. The extension completes the interactive OIDC stage before extension-owned Quick Access renders the enrollment passphrase field. The passphrase never crosses a web-page/content-script channel, never uses `passbolt.passphrase.request`, never invokes remember-passphrase behavior, and is cleared from the Quick Access form before the asynchronous enrollment request completes. The background cryptographic service validates it directly against the local encrypted OpenPGP private key. It generates fresh keys and identifiers, computes `C1 = AES-256-GCM(KD, P, innerAAD)` and `C2 = AES-256-GCM(KS, C1, outerAAD)`, and signs the fixed enrollment transcript with the existing OpenPGP key. The API verifies session, CSRF, identity ownership, freshness, context, transcript signature, fingerprint, suite, and uniqueness before encrypting `KS` and atomically committing the enrollment. Local persistence happens only after that commit.

## Login and release

Login starts in the extension with a fresh client nonce and ephemeral HPKE recipient key. A request-bound device-login transcript is signed with the profile-resident enrollment signing key. After server verification, every unlock creates a five-minute OIDC transaction with `prompt=login`, `max_age=0`, an essential configured ACR, fresh state/nonce/PKCE, and no refresh token or silent flow. `auth_time` must fall within the server transaction window with at most 60 seconds skew; returned ACR must match exactly. The transaction configuration hash is keyed by the transaction-encryption key and includes the OIDC client secret, so rotation of either secret invalidates every in-flight transaction without persisting either secret.

The callback creates only a one-time release capability. A second signed request atomically consumes it. The API decrypts `KS`, HPKE-seals it to the request-bound ephemeral recipient using the release-package binding, then discards plaintext `KS`. The extension opens the package, decrypts `C2` with `KS`, decrypts `C1` with `KD`, checks context and fingerprint, decrypts the existing OpenPGP private key locally, and invokes unchanged GPGAuth. Before successful final GPGAuth, the recovered passphrase remains transient and is not written to Passbolt passphrase storage. After GPGAuth succeeds, the extension mirrors native login with `rememberMe=false`: it places the passphrase in Passbolt's standard `browser.storage.session` cache with a 60-second alarm, then invokes post-login setup. It never selects session-long remember-me behavior. Share, decrypted-key, HPKE-private-key, and release-capability material is cleared best-effort after use.

## Revocation, logout, and rotation

Identity unlink is a normal authenticated, CSRF-protected, explicitly confirmed transaction. It locks the identity and enrollment rows, revokes and deletes enrollments and encrypted shares, then deletes the identity and returns enrollment identifiers for local cleanup. The normal encrypted OpenPGP key is untouched. Offline profile clones retain local artifacts but cannot obtain revoked `KS`.

Logout removes the standard short-lived passphrase cache, server share, decrypted OpenPGP objects, ephemeral HPKE keys, and release capabilities. It retains the profile-resident enrollment keys and encrypted client envelope. Enrollment passphrases are never placed in Passbolt passphrase storage. A login-recovered passphrase is stored only after successful final GPGAuth, in `browser.storage.session` for the native `rememberMe=false` 60-second policy; it is never written to `browser.storage.local`, IndexedDB, cookies, page/content-script state, or server persistence. Because browser alarms are scheduler-driven, 60 seconds is the requested cleanup interval rather than a hard real-time destruction guarantee.

Passphrase or OpenPGP-key rotation revokes affected enrollments and requires re-enrollment. The extension first validates and locally prepares the existing Passbolt key update. Before the update crosses its success boundary, an authenticated and CSRF-protected plugin endpoint locks the current user's `users` row, creates or reactivates a unique per-user `active` rotation barrier, invalidates every in-flight enrollment/release request and OIDC result, overwrites every protected server-share field, and marks every enrollment revoked in the same database transaction. The endpoint returns a random 256-bit capability whose hash is authoritative and whose retry copy is authenticated-encrypted at rest. An active begin is idempotent so a lost response does not strand a normally authenticated user.

Every enrollment/release start, enrollment commit, and final share release locks the same user row before creating or locking dependent state and rechecks that no active barrier exists. Consequently, a start or commit ordered before the barrier is created is invalidated by the barrier transaction, while one ordered after it is rejected. A release ordered before the barrier may finish; none ordered after it can decrypt `KS`. The transactional commit/release check remains the final authoritative control.

After barrier activation, the extension immediately deletes the returned local browser-profile enrollments and only then invokes the existing private-key update. If the key update fails before its persistence boundary, the extension capability-finishes the barrier as `failed`; old server shares remain overwritten and are never restored. After the key update succeeds it capability-finishes as `completed`. A lost or failed completion response leaves the barrier active and SSO unavailable until a normally authenticated retry resolves it. Normal passphrase/GPGAuth login remains available throughout. The passphrase-update controller does not replace a keypair, so its fingerprint ordinarily remains unchanged; revocation is triggered by the passphrase operation itself, never inferred from fingerprint change. As a separate defense for actual key replacement/recovery, the plugin listens for persisted GPG-key material changes and revokes the user's old-fingerprint enrollments in the surrounding database transaction. Start and final release also require the enrollment fingerprint to remain a current nondeleted GPG key.

Issuer or subject changes require explicit identity re-linking and a new enrollment. KEK rotation rewraps `KS` under the new active key ID. Protocol upgrades create versioned new enrollments and never downgrade silently.

## Accepted first-release trust model

Desktop Chrome/Chromium is the only supported browser. A copied enrolled browser profile, qualifying fresh Keycloak authentication, and an honest available Passbolt API are sufficient for SSO unlock. The profile keys provide no platform-keystore binding, no resistance to profile copying, and no proof of a physical device.
